# 30 — 기술 스택

`20-프로토타입-1차.md` 6장이 미뤄둔 결정에 답한다. 1단계 착수와 함께 정했다.

---

## 1. 한 줄 요약 `[확정]`

```
서버   Java 21 · Maven · 순수 도메인 코드 + 6단계부터 Spring Boot
클라   Phaser 3 (TypeScript) — WebGL 캔버스. 브라우저에서 돈다
배포   링크 하나. 지인들이 폰으로 연다
```

**서버가 JSON만 내려주고 화면은 클라이언트가 전부 그린다.**
서버가 HTML을 그려 내려주는 방식이 아니다 — 이게 이 프로젝트의 가장 중요한 구조 결정이다.

그 경계를 어디에 긋고 어떻게 지킬지는 **`31-서버와-클라이언트-경계.md`** 에 규칙으로 적어 뒀다.

## 2. 서버 `[확정]`

| 항목 | 선택 | 이유 |
|---|---|---|
| 언어 | **Java 21** | 익숙한 것. `switch` 패턴 매칭과 레코드 패턴을 쓴다 |
| 빌드 | Maven | 같은 이유 |
| 데이터 | YAML (`resources/data/`) | 밸런스를 빌드 없이 고친다 |
| 테스트 | JUnit 5 + AssertJ | |
| 프레임워크 | **1~3단계에는 없음** | 아래 참조 |
| DB | **1~5단계에는 없음** | 아래 참조 |

### 왜 1단계에 Spring Boot 를 안 넣는가

1~3단계는 HTTP 도, 화면도, 로그인도 없다. **경제가 안 망가지는지 재는 단계**다.
프레임워크를 넣으면 테스트마다 컨텍스트가 뜨고, 그만큼 밸런스 한 바퀴가 느려진다.
프로토타입의 유일한 기능 요구사항이 **밸런스를 바꾸기 쉬운 것**이라
(`20` 5장) 여기에 드는 마찰을 제일 먼저 없앤다.

지금 도메인 코드에는 **프레임워크 의존이 하나도 없다.**
그래서 4단계에서 Spring Boot 를 얹을 때 `pom.xml` 과 앱 클래스만 늘고 도메인은 그대로다.

### 왜 DB 를 안 넣는가

1~5단계에 저장할 게 없다. 세계는 시작 시각과 데이터 파일에서 **다시 만들어낼 수 있고**,
플레이어 상태가 생기는 건 6단계다. 그때 MariaDB + Flyway 를 붙인다 — 포켓링크와 같은 구성이라
운영 경험이 그대로 넘어온다.

지금 구조가 이걸 이미 준비하고 있다. 세계 상태는 **절대 시각 + 틱 번호**로만 표현되므로
(`03` 2장, `World.advanceTo`) 나중에 마지막 틱만 저장해두면 재기동해도 이어진다.

## 3. 클라이언트 `[확정]`

**Phaser 3 (TypeScript).** 브라우저에서 WebGL 캔버스에 그린다.

### 웹인데 왜 "진짜 게임"이 되는가

웹이라서 제한적인 게 아니다. **서버가 HTML 을 그려 내려주는 방식**이라서 제한적인 것이다.
그 방식에서는 화면이 페이지 단위로 갈리고 게임 루프가 없고, 연출을 CSS 로 해야 한다.
CSS 는 파티클에 맞지 않는다 — 비를 만들면 잘해봐야 `div` 몇 개가 떨어지고, 개수를 늘리면 폰에서 버벅인다.

Phaser 는 다르다. **HTML/CSS 가 아니라 WebGL 캔버스에 그린다 — Godot 웹 익스포트와 같은 렌더링 방식이다.**

| 되는 것 | |
|---|---|
| 스프라이트 시트 애니메이션 | 캐릭터가 실제로 움직인다 |
| 파티클 | 비 · 눈 · 먼지 · 타격 이펙트. 수천 개를 GPU 가 처리한다 |
| 셰이더 | 화면 전체 색조, 밤낮, 물결 |
| 트윈 · 카메라 | 화면 흔들기, 줌, 팬 |
| 타일맵 | 도시 · 노선 지도 |
| 사운드 | |

화면 전부를 Phaser 로 그린다. 표와 목록도 캔버스 위에 게임 UI 로 만든다
(`rexUI` 같은 UI 플러그인이 있다). **문서 화면이 아니라 게임 화면이 되어야 한다.**

### 왜 Godot 이 아닌가

Godot 4 는 좋은 엔진이다. 에디터로 씬과 애니메이션을 눈으로 짜는 이점이 분명히 있고,
한 프로젝트에서 웹 · 안드로이드 · PC 를 전부 뽑을 수 있다. **졌지만 근소한 차이다.**

갈린 이유는 하나다 — **주력이 폰이다.**

| | Phaser 3 | Godot 4 웹 |
|---|---|---|
| 빌드 크기 | 수 MB | **25~40MB** |
| 모바일 브라우저 | 안정적 | 4.3 이후 나아졌지만 여전히 불안정. **iOS 사파리가 특히** |
| 서버 요구사항 | 없음 | **COOP/COEP 헤더 필요** (SharedArrayBuffer) |
| 한글 IME | 정상 | 웹 익스포트에서 매끄럽지 않다 |
| 에디터 | **없음 — 코드로 짠다** | 있다 |
| 2D 연출 | 충분 | 더 편하다 |

**Phaser 가 지는 건 에디터 하나다.** 씬과 애니메이션을 코드로 짜야 한다.
그 대신 폰에서 확실히 돌고, 지인들이 링크를 눌렀을 때 몇 초 안에 뜬다.

나중에 PC 위주로 바뀌거나 폰에서 Godot 이 쓸 만해지면 **서버는 그대로 두고 클라이언트만 갈아끼운다.**
서버가 JSON 만 내려주는 구조라 이게 가능하다 — 다만 **가능하다는 것과 실제로 되는 것은 다르다.**
경계가 새면 규칙이 클라이언트에 반쯤 들어가 있게 되고 그때는 갈아끼울 수 없다.
그래서 `31` 에 규칙을 따로 적어 뒀다.

> Phaser 를 **프로토타입용으로만 볼 것인지, 잘 되면 그대로 갈 것인지**는 아직 정하지 않았다 `[미결]`.
> 전자로 못 박으면 Phaser 에 드는 투자를 최소로 한다 — UI 프레임워크를 정성껏 짜지 않고
> 에셋 파이프라인도 Phaser 에 맞춰 고정하지 않는다.
> 어느 쪽이든 **경계를 엄격히 한다는 결론은 같아서** 6~7단계에 클라이언트를 시작할 때 정하면 된다.

### 왜 모바일 앱(APK)이 아닌가

지인 몇 명에게 나눠주는 게임이라 **배포 마찰이 개발 속도를 직접 깎는다.**

* 안드로이드 — APK 를 보내면 되지만, **밸런스 숫자 하나 바꿀 때마다 새 APK 를 다시 보내야 한다.**
  프로토타입은 숫자를 하루에도 몇 번씩 고치는 단계라 이 마찰이 치명적이다
* 아이폰 — 사이드로딩이 안 된다. TestFlight(연 $99, 빌드 90일 만료)나 앱스토어 심사가 필요하다.
  **지인 중 한 명이라도 아이폰이면 여기서 막힌다**

웹은 링크 하나고, 고치면 새로고침으로 반영된다.
그리고 앱이 필요했던 이유 두 가지는 웹에서도 된다 — **PWA 로 홈 화면에 추가**하면 앱처럼 열리고,
**웹 푸시**로 "캐러밴이 셀리아에 도착했다" 알림을 보낼 수 있다
(안드로이드는 그냥 되고, 아이폰은 홈 화면에 추가한 경우에만 된다).

## 4. 에셋 `[미결]`

`90` 4장이 지적한 대로 **비용이 가장 큰 항목**이고, 고유 캐릭터 수를 정하는 것도 이쪽이다.

후보: itch.io, Kenney(CC0), OpenGameArt. 중세 상인 · 마을 · 캐릭터 초상화 계열 2D 팩이 많다.

지금 정할 필요는 없다. 다만 **8단계(각성 연출) 전에는 정해야 한다** —
`08` 3장에 따르면 그 그림이 곧 보상이라, 그림 없이는 "왜 이 캐릭터를 얻고 싶은가"를 검증할 수 없다.

## 5. 단계별로 무엇이 늘어나는가

| 단계 | 서버 | 클라이언트 |
|---|---|---|
| 1~3 | 순수 Java + 콘솔 | **없음** |
| 4~5 | 그대로 | 없음 |
| 6~7 | **+ Spring Boot (JSON API)** · **+ MariaDB** | **+ Phaser 프로젝트 시작** |
| 8 | 그대로 | **+ 에셋 · 전투 연출** |

화면을 8단계까지 미루는 건 의도적이다 (`20` 4장).
그림에 시간을 쓰기 시작하면 밸런스를 바꾸기 싫어지고, 프로토타입은 밸런스를 바꾸려고 만드는 것이다.
